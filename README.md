# \## Data findings

# 

# Source: `outputs/part\_a\_checks.csv`, `part\_a\_delay\_by\_group.csv`, `part\_a\_correlations.csv`. 1,224 raw rows became 1,200 after removing 24 duplicates; 278 parcels (delay\_rate 0.2317) were delayed.

# 

# 1\. \*\*Service type.\*\* Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897. Standard is 0.2056 and Economy 0.0857.

# 2\. \*\*Hub tier.\*\* Delay rate climbs from 0.0400 (Tier 1) to 0.2150 (Tier 2) to 0.4400 (Tier 3).

# 3\. \*\*Distance.\*\* Delay rate rises steeply with distance: 0.0219 (0-200 km), 0.1368 (201-400), 0.4364 (401-600), 0.8523 (601+).

# 4\. \*\*Strongest correlations with delivery\_hours\*\* (by absolute value, excluding itself): promised\_hours +0.8372, distance\_km +0.4013, n\_stops +0.3247. (hub\_daily\_capacity is next at -0.3237.)

# 5\. \*\*Why log-transform declared value.\*\* On the median-filled column the mean is 1533.05 INR against a median of 1121.5 INR (a right-skewed tail); after the natural log they are 7.0277 and 7.0224, almost identical, so the feature is near-symmetric.

# 

# Cleaning also found 5 sentinel weights (999 kg, treated as missing), 12 service\_type spellings collapsed to 3, and 1 delivery-hours outlier by the 1.5 x IQR rule (bounds -0.7063 / 116.5238).

# \## Model results (regression)

# 

# Split 840 / 180 / 180. The scaler was fitted on training rows only: `train\_scaled\_max\_abs\_mean` is 0.0 while `test\_scaled\_max\_abs\_mean` is 0.2187.

# 

# \- \*\*Baseline.\*\* Predicting the training mean gives validation R2 = -0.0212 (RMSE 18.8552 hours): it explains nothing, so any real model must beat this.

# \- \*\*Validation winner.\*\* Linear regression, RMSE 4.8912 hours, R2 0.9313. Gradient boosting is essentially tied (4.9165, 0.9306); random forest 5.5095 (0.9128); the depth-6 decision tree 6.2796 (0.8867).

# \- \*\*Bias vs variance (tree depth).\*\* Depths 1, 2 and 3 are high-bias: train and validation RMSE are both high (depth 1: 11.6334 / 12.1324) with small gaps (0.4990, 1.0427, 1.1738). Depths 12 and unlimited are high-variance: unlimited depth has train RMSE 0.0000 but validation 7.8368 (gap 7.8368), depth 12 has a gap of 5.9927. Depth 8 is already drifting (gap 3.4541). Depth 6 had the lowest validation RMSE (6.2796).

# \- \*\*Learning rate.\*\* 0.1 is best (val R2 0.9306, RMSE 4.9165). At 0.01 the 100 trees move too little and the model underfits (R2 0.7127, too slow); at 1.0 each tree overcorrects and the ensemble overshoots (R2 0.8440).

# \- \*\*Cross-validation disagrees.\*\* On the 1,020 training+validation rows with one shared KFold, gradient boosting scores mean R2 0.9353 (std 0.0045) against linear regression 0.9261 (std 0.0048). The rule-based final model is linear regression (lowest validation RMSE); scored once on test it gives RMSE 4.5235 hours and R2 0.9493. If I were choosing what to ship, I would pick gradient boosting: the CV estimate uses about six times more held-out rows than the 180-row validation set, and the validation gap between the two models is only 0.0253 hours of RMSE, which is noise. Boosting can also capture interactions a linear model cannot. The gap in CV (0.0092 R2) is about two standard deviations, so it is a modest preference, not a decisive one; linear regression remains a strong, simple fallback.

# \## Model results (classification)

# 

# Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

# 

# \- \*\*Blind baseline.\*\* Predicting "on time" for every parcel gives validation accuracy 0.7667 (TN 138, FN 42, TP 0), yet it catches 0 delayed parcels (recall 0). Accuracy rewards it only because 23% of parcels are delayed.

# \- \*\*Models at the 0.5 rule.\*\* Logistic regression F1 0.8046; decision tree depth 6 F1 0.7470; default forest F1 0.7848. All have accuracy 0.8833-0.9056, above 0.7667.

# \- \*\*Noise columns.\*\* The five bookkeeping columns hold a combined 0.2245 of the 17-column forest importance, even though they carry no signal. All five fall outside the top 7 by F-score (ranks 8, 12, 14, 16, 17; the largest noise F-score is 4.5847, while the smallest F-score in the top seven is 36.7281). The forest spreads importance over noise because it can always find chance splits; F-scores expose it.

# \- \*\*SelectKBest.\*\* Validation F1 for k = 5, 7, 10, 12, 17 is 0.6988, 0.8333, 0.7857, 0.8049, 0.7848. k = 5 drops real signal; k = 7 keeps exactly the true seven columns and is best, though the differences among 10, 12 and 17 are small.

# \- \*\*Tuning.\*\* It did not beat the untuned forest on 7 features: grid search 0.7750 (best CV accuracy 0.8952), randomized search 0.7848 (0.8905), default forest 0.8333. With only 42 delayed parcels in validation, one parcel moves F1 by about 0.01-0.02, so these differences are within noise; tuning on a set that small mostly selects luck. The final configuration is the default forest (n\_estimators 100, no depth limit, min\_samples\_leaf 1) with k = 7.

# \- \*\*Threshold.\*\* The highest threshold with validation recall >= 0.80 is \*\*0.5\*\* (precision 0.7955, recall 0.8333, F1 0.8140). At 0.6 recall falls to 0.7619; at 0.3 recall is 0.9286 but precision drops to 0.6964.

# \- \*\*One test evaluation at 0.5.\*\* Precision 0.6889, recall 0.7561, F1 0.7209 (TN 125, FP 14, FN 10, TP 31). Test recall is lower than validation recall (0.7561 vs 0.8333): about 3 more missed parcels out of roughly 41. With so few delayed parcels in the test set a swing of this size is expected, so the honest reading is "recall around 0.75-0.85", not exactly 0.76.

# \## Operations recommendation

# 

# \- \*\*Escalate segment\*\* (9 hubs, mean delay rate 0.4600, mean delivery 64.65 hours): HUB13 Nagpur (0.46), HUB15 Kochi (0.36), HUB17 Patna (0.46), HUB18 Ranchi (0.38), HUB19 Guwahati (0.62), HUB20 Raipur (0.48), HUB21 Bhubaneswar (0.40), HUB23 Siliguri (0.44), HUB24 Agartala (0.54). Watch has 8 hubs (delay rate 0.1550); Standard has 7 (0.0257).

# \- \*\*Tier labels that mislead\*\* (`tier\_vs\_segment\_mismatch.csv`): HUB07 Kolkata is Tier 1 but behaves like Watch (0.14); HUB13 Nagpur and HUB15 Kochi are Tier 2 but behave like Escalate; HUB22 Dehradun is Tier 3 but behaves like Watch (0.20). The tier label is a size/capacity description and should not drive playbooks; use the behavioural segment instead, and review these four hubs' labels.

# \- \*\*Alert threshold 0.5.\*\* On the held-out test set, of every 10 flagged parcels about 7 (6.9) are really delayed (precision 0.6889), and of every 10 delayed parcels about 8 (7.6) are caught (recall 0.7561).

# \- \*\*New parcels.\*\* 8 of the 48 new parcels are flagged; 6 of those are in Escalate hubs and need a hub-manager escalation (SHP90002, SHP90003, SHP90011, SHP90025, SHP90041, SHP90046), the other 2 get a proactive customer call.

# \- \*\*Why K = 3.\*\* `part\_d\_separation.csv` gives across/within ratios of 2.8940 (K=2), 5.3928 (K=3), 6.3047 (K=4), 6.8866 (K=5). The big jump is from 2 to 3 (+2.50); beyond that gains are small (+0.91, +0.58). K = 4 (sizes 8-7-5-4) and K = 5 (8-7-4-3-2) each contain a cluster of fewer than 6 hubs, too small to carry its own playbook, and operations runs exactly three playbooks.

# \## Production plan

# 

# \*\*(a) Production-readiness mapping\*\*

# 

# | Characteristic | Item in this repository |

# |---|---|

# | Accuracy | Held-out test metrics in `part\_b\_metrics.csv` and `part\_c\_final\_test.csv`; threshold chosen on validation only |

# | Reliability | `clean\_shipments` handles gaps, duplicates, sentinels, spelling variants; `part\_a\_checks.csv` shows 0 nulls in features |

# | Reproducibility | Pinned `requirements.txt`, fixed `random\_state` everywhere, deterministic `predict\_delay.py` |

# | Performance (speed) | A 100-tree forest on 7 features scores 48 parcels in well under a second; no external services |

# | Maintainability | Shared code in `src/shipment\_prep.py`, one script per Part, config in `part\_c\_final\_config.csv` |

# | Consistency | Training and scoring both call `clean\_shipments` and `build\_features`; `feature\_order.csv` fixes column order; `impute\_values.csv` stores training medians |

# | Monitorability | `part\_d\_reload\_check.csv` and the quantities below |

# 

# \*\*(b) Quantities to monitor\*\*

# 

# \- Weekly delayed share of delivered parcels: alert if it moves more than 5 percentage points from the training rate of 0.2317 for two consecutive weeks.

# \- Weekly share of parcels flagged: alert if it leaves 0.15-0.30 (validation flags 41 of 180, about 0.23).

# \- Recall on parcels whose outcome is now known (rolling 4 weeks): alert if below 0.65 (test recall was 0.7561); precision below 0.55 as a second trigger.

# \- Input drift: any feature's weekly mean moving more than 3 training standard deviations, or more than 2% of parcels hitting the sentinel or missing-value path.

# 

# \*\*(c) Retraining and drift.\*\* Retrain monthly on all delivered parcels with known outcomes, and immediately if two monitors trip. The 15-28 September sale window (`sale\_event\_flag`) should be compared against the same kind of event (last year's sale, or the prior sale), not ordinary weeks, because Express parcels run slower in it by design; its own delay rate and flag share will legitimately be higher. Drift here would look like new distance or stop distributions (new lanes, route changes), hubs moving between segments (rerun `part\_d\_segments.py` each retrain), or a shift in service mix.

# 

# \## Limitations

# 

# 1\. \*\*Synthetic data.\*\* Delays follow a generator with known structure, so real-world noise, hub-level shocks and time trends are absent; performance on real shipments would be lower.

# 2\. \*\*Tiny test set.\*\* Only 41 delayed parcels in test: precision and recall have wide confidence intervals (one parcel changes recall by about 0.024).

# 3\. \*\*Threshold tuned on one validation split.\*\* Threshold 0.5 and the forest-vs-tuned choice rest on 42 delayed validation parcels and may not repeat on another split.

# 4\. \*\*Hub segments use 50 parcels per hub.\*\* Delay rates have a granularity of 0.02 and can shift with sampling; segments are a snapshot, not a stable property.

# 5\. \*\*Single time window.\*\* All parcels come from three months; seasonality beyond the one sale window is not seen.
